@CHAPTER What comes out
@INTRO Four things with one prefix, two APIs, and one rule: they travel together or not at all.

@SECTION The set

One `--compile` produces four things, all named from the `--output` prefix:

@FRAG
output\dense-int8.pb          the emitted source
output\dense-int8.pmw         the checked weight pack
output\dense-int8.json        the manifest
output\dense-int8.runtime\    the execution sources this model needs
@ENDFRAG

On a bare-metal target the source has that target's extension instead -
`.pi4` for Pi 4 and UNO Q, `.pico`, `.pico2` - and the runtime folder holds
different files. The shape is the same.

@TRAP These four are **one artefact in four files**. The source contains
the weight pack's CRC and identity; the pack has to be that exact file;
the runtime folder is the version of the runtime this source was written
against. Mix a source from one generation with a pack or a runtime from
another and you will be told, but you will be told at bind time on the
target rather than at your desk. Use a new prefix per generation and keep
the set together.

@SECTION The emitted source, from the top

@FRAG
; Generated by the PureMetal ONNX ahead-of-time compiler.
; Model: dense.onnx
; Backend: Host-language source for a native Windows x64 application
; Executable tensor code; no ONNX graph interpreter is present at runtime.
EnableExplicit
#PMO_USE_BATCHNORM = 0
#PMO_USE_STFT = 0
#PMO_USE_RESIZE = 0
#PMO_USE_CONVTRANSPOSE = 0
#PMO_USE_CONV = 0
#PMO_USE_LSTM = 0
#PMO_USE_INT8 = 0
XIncludeFile "dense-fp32.runtime/tensor_fp32_windows.pbi"
@ENDFRAG

The `#PMO_USE_...` switches are the model saying what it needs. This graph
is one `MatMul`, so convolution, the LSTM, the short-time Fourier
transform and the rest are switched off, and the compiler underneath will
not build code for them. On a part with 264 KiB of RAM that is not a
micro-optimization; it is the difference between fitting and not.

Then the constants that describe the memory:

@FRAG
#PMO_WEIGHT_FILE_BYTES = 144      ; the pack's exact length
#PMO_WEIGHT_DATA_BYTES = 16       ; payload after the 128-byte header
#PMO_ARENA_BYTES = 128            ; working memory this model requires
#PMO_INT8_SCRATCH_OFFSET = 0
#PMO_INT8_SCRATCH_BYTES = 0
#PMO_STFT_SCRATCH_BYTES = 0
@ENDFRAG

Use those symbols in your application. They are generated from the same
plan the code was generated from, so they cannot drift from it; a number
you copied into your own header can.

@SECTION The weight pack, and why the source checks it

`.pmw` is a checked container: an eight-byte magic, a version, a
128-byte header, the payload, and a CRC-32 over the payload. The emitted
source contains a validator that reads it byte by byte before accepting
anything:

@FRAG
Procedure.i PmOnnxValidateWeights(*weights, bytes.i)
  If *weights = 0 Or bytes <> #PMO_WEIGHT_FILE_BYTES : ProcedureReturn 0 : EndIf
  ... magic, version, header length ...
  ... the model's own SHA-256 identity, word by word ...
  If PmTensorCrc32(*weights + 128, #PMO_WEIGHT_DATA_BYTES) <> $D793D46B
    ProcedureReturn 0
  EndIf
  ProcedureReturn 1
EndProcedure
@ENDFRAG

Three separate things have to agree: the length, the identity of the model
this pack was built from, and the CRC of the payload. The identity check
is the one that earns its keep. A pack of the right length with the right
CRC can still be the wrong model's weights, and inference against the
wrong weights does not crash - it produces confident nonsense.

@NOTE A CRC over hundreds of megabytes is not free. On a Pi 4, a full
CRC-32 pass over the pinned speech model's 324,621,440-byte pack was
measured at about **1.95 seconds** with caches enabled, and vastly slower
without them. That is a bind-time cost paid once, which is one more reason
the model stays resident.

@SECTION The manifest

The `.json` is the accounting. It is not needed at runtime; it is there so
you can answer "will this fit" and "what exactly did I generate" without
reading the source.

@FRAG
"precision": "int8",
"model_sha256": "71a76b66...",
"execution_contract": "resident-reusable",
"shape_contract": "fixed-dimensions-variable-input-values",
"weight_bytes": 196,
"arena_bytes": 256,
"decoded_weight_reserve_bytes": 0,
"reduced_storage_weight_count": 0,
"int8_scratch": {"offset":128,"bytes":128},
"ai_onnx_opset": 20,
"inputs":  [{"index":0,"name":"x","type":"float32","shape":[1,2],"bytes":8,"storage":"arena","offset":0}],
"outputs": [{"index":0,"name":"y","type":"float32","shape":[1,2],"bytes":8,"storage":"arena","offset":64}],
"quantization": {
  "mode": "int8",
  "scheme": "per-output-channel symmetric signed INT8 weights, dynamic per-row signed INT8 activations, INT32 accumulation, FP32 operator seams",
  "weight_count": 1, "fp32_weight_bytes": 16, "int8_weight_bytes": 4
},
"packed_tensors": [ {"name":"w","type":"int8","shape":[2,2],"offset":192,"bytes":4}, ... ]
@ENDFRAG

Four fields answer the questions people actually ask.

`arena_bytes` is the working memory. `weight_bytes` is the pack.
`decoded_weight_reserve_bytes` is what FP16, BF16 or INT4 will occupy
after decoding - the number chapter 4's trap is about, reported
separately so it cannot hide inside the storage saving. And
`quantization.weight_count` tells you how much of your model INT8 really
touched: two weights out of two hundred is a fact worth knowing before you
draw a conclusion about speed.

`shape_contract` names which of the two emitters ran:
`fixed-dimensions-variable-input-values` or `runtime-dimensions`.

@SECTION The runtime folder

The tool copies out the execution sources the emitted model includes. They
are not a library you installed; they are a snapshot taken at generation
time and they belong to that generation.

@FRAG
dense-fp32.runtime\        (windows)
  tensor_dynamic_windows.pbi   tensor_fp32_windows.pbi   tensor_simd_windows.pbi
  tensor_pool_windows.pbi

dense-pi4.runtime\         (pi4 / unoq)
  math.pmi   tensor_fp32.pmi   tensor_fp32_neon.pmi
  tensor_trig_a64.pmi   tensor_dynamic_portable.pmi
@ENDFRAG

@TRAP An already-generated application does not pick up a runtime fix. Its
runtime is the copy sitting beside it. To adopt a change: rebuild the
generator (chapter 2), regenerate the model's whole set into a fresh
prefix, and build the application again. Copying one newer file into an
old runtime folder is the worst of the available options, because the
source and the runtime then disagree about a contract and nothing checks it.

@SECTION Two APIs, and how to tell which you got

**Fixed shapes give you `PmOnnx...`, and it allocates nothing.**

@FRAG
PmOnnxBindMemory(weights, weightBytes, arena, arenaBytes)  ; check the result
PmOnnxInputAddress(index)      ; fill this buffer, declared type and shape
PmOnnxExecuteBound()           ; check the result
PmOnnxOutputAddress(index)     ; read before the next execution
PmOnnxLastErrorNode()          ; which node failed
PmOnnxUnbindMemory()           ; before you free anything
PmOnnxSetThreads(n)            ; Windows: at most n worker threads (see below)
@ENDFRAG

You supply aligned, non-overlapping weight and working buffers, sized from
`#PMO_WEIGHT_FILE_BYTES` and `#PMO_ARENA_BYTES`, and they must stay valid
for the model's whole life. Binding does not take ownership of them. The
bind refuses overlap in either direction rather than trusting you.

**Runtime dimensions give you `PmModel...`.**

@FRAG
PmModelInitialize(weightPath)   ; Windows: reads the pack from disk
PmModelBindMemory(w,wb,a,ab)    ; portable: you supply both, as above
  PmModelResetRequest()         ; release the previous request's tensors
  PmModelInput(index)           ; a tensor ID; declare this request's dims
  PmModelExecute()              ; check the result and DError
  PmModelOutput(index)          ; read while its storage is live
PmModelClose()
PmModelSetThreads(n)            ; Windows: at most n worker threads (see below)
@ENDFRAG

@TRAP `DError` is a string on Windows and an ASCII string POINTER on the
portable targets. The same field name, two different things, because the
portable runtime has no string type to hand. Code that walks it assuming
one will misbehave on the other. Chapter 3's example shows the Windows
form.

@SECTION A model with random operators

A model with a random node gains one procedure, a manifest entry and the
generator's source in its runtime folder. A model without one gains nothing:
its source closure is byte for byte what it was.

@FRAG
PmOnnxSetRandomSeed(seed)      ; fixed shapes: 1, or 0 for a seed wider than 32 bits
PmModelSetRandomSeed(seed)     ; runtime dimensions: the same
@ENDFRAG

The model seed is 32 bits and starts at 0. On a 64-bit target any value
whose upper half is all zeros or all ones is accepted, so `-1` and
`$FFFFFFFF` are the same seed everywhere; anything wider is refused rather
than truncated. A node with its own `seed` attribute keeps it and is not
moved by the model seed.

Every execution that starts the graph uses the next **request number**:
0 after the model is bound, then 1, 2 and so on, so each request draws new
values. Setting the seed restarts the numbering at 0, and binding again
restarts it too and keeps the seed. The same seed and the same sequence of
requests reproduce the same values, request for request.

@FRAG
"random": {"mode":"generated","set_seed_procedure":"PmOnnxSetRandomSeed",
  "model_seed_default":0,"model_seed_bits":32,
  "request_numbering":"0 after the model is bound or its seed is set; one more for every execution that starts the graph",
  "generator":"threefry2x32-20", ...,
  "nodes":[{"index":0,"name":"","op":"RandomNormal","output":"a","mean":0.000000000,"mean_bits":"0x00000000",
            "scale":1.000000000,"scale_bits":"0x3F800000","seed":"model","dtype":1},
           {"index":1,"name":"","op":"RandomUniform","output":"b","low":0.000000000,"low_bits":"0x00000000",
            "high":1.000000000,"high_bits":"0x3F800000","seed":"attribute","seed_bits":"0x40A00000","dtype":1}]}
@ENDFRAG

`index` is the node's position in the graph, which is part of the key its
values come from. With `--random-inputs` the mode is `inputs`, there is no
seed procedure and no generator source, and each node carries the
`input_index` you fill.

The runtime folder gains `tensor_random.pmi`, the generator - one source,
included unchanged on every target - and the runtime-dimension wrapper for
the target, `tensor_random_dynamic_windows.pbi` or
`tensor_random_dynamic_portable.pmi`.

@SECTION Threads on Windows

A Windows model runs on every logical processor its process may use. The
count is taken when the model is bound, on the machine it is running on,
not when it was compiled, and it is the process's own allowance, not the
machine's: the affinity mask the process was started with (`start
/affinity`, a job object's affinity, a parent's mask), every active
processor of every processor group when the process has not been narrowed
to part of one, and lower again when the process has a default CPU set.
Started with `start /affinity 0xF` on a 32-processor machine, the same
program uses 4 threads.

Binding takes the workers - `PmModelInitialize` and `PmOnnxBindMemory` do
it - creating any that do not exist yet. `PmModelClose` and
`PmOnnxUnbindMemory` park every one of them before they return: each is
blocked on its own semaphore, runs nothing and holds no working buffer, and
the next bind takes it again. No operator creates a thread, and no worker
runs outside a bound model's operators.

Workers are parked rather than ended because ending them made the program's
own exit fault: a thread of this runtime that has run procedures leaves work
for Windows' thread-pool workers when it ends, and a program that ends soon
after races them. With fault dialogs switched off, as a test harness does,
89 of 600 exits of a twelve-line program with no model in it reported an
access violation; with the threads blocked instead, none did.

Two settings can lower the count; nothing raises it past the allowance:

@FRAG
--threads N              compile option, Windows only: at most N threads;
                         1 runs the model on the calling thread alone
PmModelSetThreads(n)     run time: at most n; 0 = every allowed processor
PmOnnxSetThreads(n)      the fixed-shape API's name for the same setting
@ENDFRAG

Both procedures return the count now in use. On a bound model the workers
are rebuilt at once; before binding the setting waits for the bind.

**The thread count never changes an output bit.** Each operator is cut
into tasks by output - elements, rows, channels, positions - and every
output value is computed by one task with exactly the arithmetic and the
summation order it has on one thread. No sum is ever divided between
threads. So 1 thread and 32 give the same bytes, and the Windows program
still agrees with the Pi 4 and the Picos wherever it did before.

An operator smaller than its measured break-even stays on the calling
thread; handing a hundred additions to 31 other threads costs more than
doing them.

@NOTE What is not split, today: the operators whose kernels are in
`tensor_ops.pmi` - the pools, the quantized products and convolutions, GRU
and RNN, and the rest of the operator set added in 2026 - run on the
calling thread. That file is one source for every target and keeps its
parameters and scratch in shared globals, so two threads cannot run it at
once without a change to it that every target would see. The bare-metal
targets keep their own core use, chapter 6.

@NOTE A program may end without closing its model - on an error path, say.
Bind returns only once every worker has started and is blocked, and a
worker between operators is always blocked, so the exit is clean. Close
the model anyway when you are done with it: that is what frees its memory
and its workers' buffers.

@SECTION The resident lifecycle, stated once

Bind once. Submit inputs. Read outputs. Release.

- **Bind** validates the pack, decodes reduced-storage weights into
  resident FP32 memory, takes the Windows worker threads, and runs the
  model's constant-preparation stage. This is where the CRC and the
  identity check are paid for.
- **Submit** fills the input buffers - or, on the runtime-dimension path,
  declares this request's shapes and then fills them.
- **Execute** runs the emitted schedule. Outputs are valid until the next
  execution or reset; they are borrowed, not given.
- **Reset** frees the request's temporaries and keeps the model. This is
  the step that makes the next request cheap, and it is the step people
  forget.
- **Close** or **unbind** releases everything and, on Windows, parks the
  worker threads. On the portable targets your buffers are still yours and
  still need freeing.

@NOTE The generated globals are ONE model instance. Serialize your calls.
There is no per-instance handle, so two threads in the same model are two
threads in the same state. Nothing in the runtime will stop you and the
result will not be an error message.

@SECTION Watching a long run, and stopping it

A resident model can run for a long time - minutes, on the speech model in
chapter 7 - and a program with a watchdog cannot simply disappear for that
long. So the reusable runtimes expose a node-boundary callback:

@FRAG
DSetProgressCallback(callback)    ; callback(phase, node) -> nonzero to continue
                                  ; 0 disables it; none installed by default

PMD_PROGRESS_BIND_BEFORE  1   node -1
PMD_PROGRESS_BIND_AFTER   2   node -1
PMD_PROGRESS_NODE_BEFORE  3   node = the generated node index
PMD_PROGRESS_NODE_AFTER   4   node = the generated node index
@ENDFRAG

Returning zero, or setting `DCancel`, asks for cancellation: the callback
unwinds normally and the operation then takes its ordinary failure path,
so you inspect `DError`, `DNode` and `DCancel` and do the normal reset.

@TRAP The callback runs synchronously on the inference thread and **must
not re-enter the model**. Every entry point rejects re-entry before it
changes any state, records an error and sets `DCancel`. Keep the callback
short. It is the right place to pet a watchdog or do required cache
maintenance; it is the wrong place to do anything that might call back in.

And be honest with yourself about what it bounds. Progress points are node
boundaries. They do not bound the time spent INSIDE one operator, one CRC
pass or one allocation - and on a large convolution that is where most of
the time is.
