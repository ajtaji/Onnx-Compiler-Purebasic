@CHAPTER Running a model on the Raspberry Pi 4: the Kokoro sentence
@INTRO One sentence of speech from the full model, on a board with no operating system, on four cores - and every step from a clean checkout to the WAV.

@SECTION What this chapter reproduces

On 2026-09-16 a Raspberry Pi 4 running the Anvil monitor, with nothing
underneath it, ran the full Kokoro-82M model of chapter 7 in FP32 on all
four cores and spoke this sentence:

@FRAG
I am the kokoro speech AI model on the raspberry Pi 4. How do I sound,
good? I am running on bare metal, with no operating system, under Anvil,
a mini kernel and boot loader, on all four cores of the Raspberry Pi 4.
Both Anvil and I were compiled by Pure Metal Forge.
@ENDFRAG

Everything that made it is published in `examples/pi4/kokoro-sentence/`:
the runner that was entered on the board, two host tools, and a README
that is the step-by-step recipe with every expected hash. This chapter is
the same path with the reasoning attached. The README is the one to follow
with a board in front of you.

@FRAG
examples/pi4/
  README.md                    the Pi 4 examples, one line each
  kokoro-sentence/
    README.md                  the recipe
    KokoroSentence.pi4         the runner - an Anvil payload
    node_output_map.pbi        a table the runner's optional NaN scan reads
    kokoro_readback.py         host tool: trace, result, dispatch count, waveform
    f32_to_wav.py              host tool: raw samples to WAV
@ENDFRAG

@NOTE The two `.py` files are developer tools for talking to a board.
Building this compiler, and generating or building a model with it, needs
no Python. The tools use the Anvil repository's own host code by path -
its console client in `tools/board_run.py` and its verified reader in
`tools/anvil_readback.py` - rather than a copy of either.

Against ONNX Runtime 1.29.0 on a PC, with the same text, the same two
pronunciation packs and the same voice, every one of the 453,000 samples

@FRAG
max absolute difference   0.259917
RMSE                      0.006588
correlation               0.996006
@ENDFRAG

@TRAP 0.26 is above the 0.1 maximum absolute difference set for the short
test sentences, and it is recorded as a failure of that limit. The board's
kernels are held bit-identical to the scalar reference, and the four-core
split was proven to return the same bytes as one core on the shorter
sentences, so the difference lies between the reference and ONNX Runtime.
Chapter 8 traces the mechanism on a shorter sentence - a tiny divergence in
the text encoder amplified into the phase of a sine with very large
arguments. This sentence is 4.4 times longer and diverges further, which
fits that mechanism; it has not been re-traced node by node.

@SECTION What you need

A Raspberry Pi 4 Model B with at least 4 GB: the runner's working memory
ends at `$A0000000`. A FAT32 USB stick or SD card for Anvil; the run booted
from a USB stick that also held the weight pack. An Ethernet cable straight
to a Windows PC. On the PC: Git, PureBasic 6.21 x64 for this compiler,
PureMetal Forge from puremetalforge.ajtaji.com for the payload, and Python
3 for the host tools, with pyserial for Anvil's upload tool. The Forge
download also includes a ready-built copy of this compiler. The 2026-09-14
copy cannot build this example; the 2026-09-17 copy can, but not the exact
payload that ran. The section after the two builds shows both.

@ENDFRAG

@TRAP **The line endings are part of the pin.** The Misaki digests are of
the files with CRLF line endings, which is what a clone with
`core.autocrlf=true` produces; the same files downloaded raw have LF
endings, a different size and a different digest, and the pack builder
refuses them before parsing a byte. The CMUdict digest is the other way
round, which is why its clone turns `core.autocrlf` off. Both clones were
run and give the digests above.

@NOTE The two files from the model repository were not downloaded again
when this recipe was followed on the desk: copies already on disk with the
same SHA-256 were used, and the two URLs were checked against the size and
SHA-256 the server publishes for each file.

@TRAP Keep the working folder's path short. The model's runtime files are
written several folders deep inside it, and a path past the classic
260-character Windows limit makes the compile fail with "Cannot create
generated runtime source", a sentence that does not mention the length
(forum topic 868, open). `$HOME\pi4-kokoro` is short enough.

@SECTION Two builds of the compiler, and why

The model source that ran was emitted by this compiler at commit
`6b6b770`. Commits after it changed runtime kernels, so they emit a
different payload - a payload built from `main` has not been run on a
board. The supplementary pronunciation pack needs `main`, because until
`b48cd05` the native packer could not build the pack its own verifier
requires. So the recipe builds both, the older one under a second name:

@FRAG
> & $pb src\PureMetalOnnxCompiler.pb /CONSOLE /THREAD /OPTIMIZER /OUTPUT bin\PureMetalOnnxCompilerCLI.exe
> git checkout 6b6b770
> & $pb src\PureMetalOnnxCompiler.pb /CONSOLE /THREAD /OPTIMIZER /OUTPUT bin\OnnxCli-6b6b770.exe
> git checkout main
@ENDFRAG

`bin\` is ignored by Git, so both executables survive the checkouts.

@SECTION The runner

`KokoroSentence.pi4` is chapter 7's resident runner in outline, made real.
Its comments walk through every step; the shape is:

@FRAG
Main():
  KrCaptureX0()              keep x0, the service table - first statement
  zero the tick rows and the KTRC trace
  KrBindServices()           check the table's magic, version and slot count,
                             take the deadman slot, and
    PmOnnxAnvilEnter(table)  hand the table to the model: four cores
  MmuBuildTables, MmuEnableCached    the payload's own page tables and caches
  PmModelBindMemory($40000000, 324621440, $60000000, 1 GiB)
  PmKokoroTextBind($54000000, ..., $55000000, ..., $56000000, ...)
  KrRender(text, $57400000)  text -> tokens -> 453,000 samples; hash them,
                             copy them out of the borrowed output tensor
  KrFinish(0)                release everything, check nothing leaked,
                             turn the MMU off, write trace stage 9, return
@ENDFRAG

Around that it keeps three records a host can read after the run: the
KTRC trace at `$57E00000`, rewritten at every node, which says how far the
run got even when the console has lost the return line; one row of
per-node timer ticks per request from `$57D00000`; and a block of result
globals whose addresses are in the `.sym` file the compiler writes beside
the image. Its return value, `x0`, is a status: 0, or a code the file's
`KrFinish` comment lists.

@NOTE The file still carries the result fields of two earlier requests,
their texts, and a per-node NaN scan that is switched off. They are
compiled in, unused, so that this source builds the exact payload that
ran; removing them is safe and changes the payload's hash.

@SECTION On the board

Anvil's boot-volume skeleton, `Boards/RaspberryPi4/sdcard` in the Anvil
repository, carries a `kernel8.img` and the rest of the card. The steps
from there are uploads, one run and a readback, and one command does all of
them from the manifest `examples/pi4/kokoro-sentence.run.json`:

@FRAG
> $tools = "$root\Anvil\tools"
> python "$tools\board_model_run.py" "$ex\..\kokoro-sentence.run.json" --console-ip $board --no-lease
@ENDFRAG

Anvil's `board_model_run.py` asks the board for the `sha256sum` of each
asset's range first and uploads only an asset whose digest differs, then
uploads the payload, arms the 15-second deadman, enters it, and the moment
it returns reads the 1,812,000 samples back, checks them against the board's
own `sha256sum` and prints `WAV ready:` with the path of
`run\<time>\kokoro-sentence.wav`. On a shared board, `--lease-file` and
`--lane` replace `--no-lease` and it takes and releases the lease itself.

@NOTE The tool was proven on a board on 2026-09-16 with the Kitten TTS
manifest beside this one (`kitten-rosie.run.json`); this Kokoro manifest has
not yet been run. The steps it replaces are below, as the run used them.

These are the commands the run used, with this recipe's paths:

@FRAG
> python "$tools\pi4_upload.py" "$root\assets\kokoro_us_english.pmg2p" --console net --console-ip $board --board-ip $board --addr 0x54000000 --cache

  (and the same for the supplement at 0x55000000 and the voice at 0x56000000)

The sha256sum is 05c30419a882ad6a094a05fe0b7bbe4e96d549c20896a5522991c652d5296f6f
@ENDFRAG

The weights did not go over the wire on the day: they had been uploaded
and verified before and saved to the USB stick as `MODEL.PMW`, and after
the reset before the run the board loaded them back. Uploading them with
`pi4_upload.py` to `0x40000000` works the same way. Either way the payload
checks the pack's header, identity and CRC-32 when it binds.

@TRAP **`board_run.py` said the payload never returned, and it had
finished.** The console lost the return line during a long silent run.
Do not run it again: read the trace. That is what the trace is for, and
what `kokoro_readback.py status` reads.

@FRAG
> python "$ex\kokoro_readback.py" cores --console-ip $board       before and after the run: the difference is the dispatch count
> python "$ex\kokoro_readback.py" status --console-ip $board      trace, status, tokens, samples
> python "$ex\kokoro_readback.py" wave --console-ip $board        board sha256sum, readback, sha256sum again
> python "$ex\f32_to_wav.py"                                      run\kokoro-sentence.wav
@ENDFRAG

`wave` saves the samples only if the board's digest before the read, the
board's digest after it and the host's digest of what arrived all agree,
and the XOR of the samples equals the one the payload computed on the
board before it copied them.

@TRAP **Two parts of this section are not yet a board transcript.**
`kokoro_readback.py` passes a self-test against a scripted console and has
not been run against a board; on the day, the waveform came back through
build 142's older `memory` dump path, which took 1,048 s. It uses the
`readback` command of Anvil build 151, which the Anvil repository measured
reading the same 1,812,000 bytes in 1.28 s. `f32_to_wav.py`, run on the
day's samples afterwards on the desk, writes the published WAV byte for
byte.

@SECTION Speaking something else

Change the bytes under `KrText3` - one `Data.a` value per UTF-8 byte - and
`#KR_TEXT3_BYTES`. PowerShell produces both:

@FRAG
> [Text.Encoding]::UTF8.GetBytes('Hello from the Pi.') -join ','
72,101,108,108,111,32,102,114,111,109,32,116,104,101,32,80,105,46
> [Text.Encoding]::UTF8.GetByteCount('Hello from the Pi.')
18
@ENDFRAG

Set `#KR_EXPECT_TOKENS3` to the sentence's token count if you know it. If
it is wrong the samples are still rendered and copied, the payload returns
320 instead of 0, and `status` prints the real count. The copy slot holds
524,288 samples, 21.8 seconds; a longer sentence is refused with 313, not
cut short. A changed runner is a different payload with a different hash.
