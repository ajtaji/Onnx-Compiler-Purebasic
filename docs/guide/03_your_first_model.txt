@CHAPTER Your first model
@INTRO Two tiny models, one command, one build, three requests - and an answer you can check by hand.

@SECTION Two models that cost nothing to get

You do not need to find a model to try this. `examples/CreateDemoModels.pb`
carries two of them as bytes in a data section and writes them to disk. Run
it once in the IDE:

@FRAG
Created output/twice.onnx: y = x + x, shape [1,N].
Created output/dense.onnx: y = x * diag(2,3), shape [1,2].
These are ONNX IR 8 / opset 20 model fixtures, not executable code.
@ENDFRAG

They are real ONNX protobuf files, not a private format that looks like
one. No package parses them into existence and nothing is downloaded - the
bytes are literally in the source, because a first example that requires
you to obtain something first is not a first example.

The two do different jobs.

**`twice.onnx`** is one `Add` node computing `y = x + x`, with the input
shaped `[1,N]`. That `N` is a named dimension, not a number, so this model
has a **runtime dimension**: the length is decided per request. It is the
one that demonstrates the resident lifecycle.

**`dense.onnx`** is one `MatMul` against a constant 2-by-2 diagonal matrix
holding 2 and 3, with the input shaped `[1,2]`. Every extent is known, so
this is a **fixed-shape** model, and it has a real weight to pack. It is
the one that demonstrates precision choices, because there is something to
reduce.

@NOTE The tool tells you which is which. Ask it:

@FRAG
> .\bin\PureMetalOnnxCompilerCLI.exe --inspect output\twice.onnx
Model:        output/twice.onnx
Bytes:        108
IR version:   8
Graph:        twice
Nodes:        1
Initializers: 0 (raw=0, typed=0, external=0)
Value infos:  0
Inputs:
  x type=1 [1,N]
Outputs:
  y type=1 [1,N]
Operators:
  Add 1
@ENDFRAG

`[1,N]` with a letter in it is the runtime dimension. `type=1` is ONNX's
number for float32. Run the same command on `dense.onnx` and you get
`[1,2]`, one initializer, and `MatMul 1`.

@SECTION Generate the Windows source

From the checkout root, one command:

@FRAG
> .\bin\PureMetalOnnxCompilerCLI.exe --compile output\twice.onnx --output output\twice --target windows
PASS: reusable source emitted to ...\output/twice.pb
Weights: ...\output/twice.pmw
Model requires one downstream build; requests use runtime dimensions.
@ENDFRAG

`--output` is a file PREFIX, not a directory and not a filename. It names
the stem that four things are built on, and the directory it sits in must
already exist:

@FRAG
> ... --output output\nodir\twice --target windows
ONNX COMPILER ERROR: output folder does not exist: ...\output/nodir/
@ENDFRAG

The tool will not create the directory for you, because a mistyped prefix
that quietly creates a folder is harder to notice than one that stops.

@TRAP **Check the exit code in scripts.** Every refusal in this book exits
nonzero, but a script that ignores that will happily go on and build the
source from the LAST successful generation. In PowerShell:
`if ($LASTEXITCODE -ne 0) { throw 'Model generation failed' }`. Using
stale output after a failed run is the single easiest way to spend an hour
debugging a change you never actually generated.

@SECTION The same thing, in the window

If you prefer, run `bin\PureMetalOnnxCompiler.exe` instead. Choose the
model, the output prefix, the Windows target and FP32 precision, and start
generation. The window runs the CLI beside it and shows you what it said -
the same text, the same result, the same files.

@SECTION Build the consumer and run it

Generation is done. Now it is an ordinary application build.

`examples/RunTwiceWindows.pb` is a complete consumer of the model you just
emitted. It includes the generated source directly:

@FRAG
XIncludeFile "../output/twice.pb"
@ENDFRAG

Open it in the IDE, enable **thread-safe executable** and the
**optimizer**, select the x64 native backend, and run it. This build is
yours; the ONNX tool played no part in it.

@FRAG
PASS request 1: 3 values doubled by one resident model.
PASS request 2: 6 values doubled by one resident model.
PASS request 3: 9 values doubled by one resident model.
All requests passed; model closed. No inference runtime DLL was loaded.
@ENDFRAG

@SECTION What actually happened in those three lines

This is a small program and it is worth reading, because its shape is the
shape of every consumer you will ever write against this tool.

@FRAG
If PmModelInitialize(root+"twice.pmw")=0     ; ONCE: load and check weights
  PrintN("Model initialization failed: "+DError)
  End 1
EndIf
baseline=DLive                               ; remember live storage now

For request=1 To 3
  n=request*3
  PmModelResetRequest()                      ; drop the previous request
  DError=""
  input=PmModelInput(0)
  If DShape(input,1,2,1,n)=0 : ... : EndIf   ; THIS request is [1,n]
  For i=0 To n-1 : PokeF(Dt(input)\Data+i*4,i+request) : Next
  If PmModelExecute()=0 : ... : EndIf
  output=PmModelOutput(0)
  ... check every value ...
  PmModelResetRequest()
  If DLive<>baseline : PrintN("Request storage was not released.") : ... : EndIf
Next

PmModelClose()
If DLive<>0 : End 1 : EndIf                  ; nothing left behind
@ENDFRAG

Three requests of 3, 6 and 9 values. One initialization. The weights were
read, checked and kept once, and the three different input lengths did not
disturb them.

Two details in there are not decoration. `DShape` is what declares this
request's dimensions - rank 2, extents 1 and n - which is exactly the
freedom `[1,N]` bought. And `DLive` is the runtime's own count of live
tensor storage: the example asserts it is back to its baseline after every
request and back to zero after the close. A leak in a resident model is
not a slow leak; it is a leak per request.

@NOTE The example checks every output value against `2*(i+request)`, not
just the first one, and not a tolerance. For an Add of float32 values that
small, the answer is exact and the test should say so. Chapter 8 is about
where tolerances are the right instrument and where they are an excuse.

@SECTION Now try a packed weight

`twice.onnx` has no weights at all, so asking for INT8 there can only
disappoint. `dense.onnx` has an eligible constant matrix:

@FRAG
> .\bin\PureMetalOnnxCompilerCLI.exe --compile output\dense.onnx --output output\dense-int8 --target windows --precision int8
PASS: generated ONNX source for windows (int8)
Source: ...\output/dense-int8.pb
Weights: ...\output/dense-int8.pmw (196 B)
Quantized weights: 1 (per-output-channel signed INT8, dynamic activation scales, INT32 accumulation)
Arena: 192 B including bounded inputs/outputs
Manifest: ...\output/dense-int8.json
Resident model: bind weights/arena once, fill inputs and execute repeatedly, then unbind when finished.
@ENDFRAG

Read those lines carefully, because they are the tool being precise rather
than enthusiastic. **One** weight was quantized. The scheme is named. The
accumulation is INT32, not INT8. And the arena figure is what this model
needs, inputs and outputs included.

@TRAP A 196-byte pack for an INT8 model where the FP32 pack was 144 bytes
is not a bug and not a failure of quantization. At this size the pack's
header, scales and alignment dominate everything else. Compression is a
property of large weight tensors; on a 2-by-2 matrix there is nothing to
compress. Draw conclusions about size from your real model's manifest,
never from a demo.

@SECTION Where to go from here

Use different output prefixes when you are comparing things. `dense-int8`
and `dense-fp32` sitting side by side can be diffed; two generations into
the same prefix cannot, and a failed second generation next to a
successful first one is a trap you set for yourself.

Then read chapter 4, which is about what the compiler will accept from a
model that you did not write yourself.
